## Remaining gaps

2. **Next arithmetic batch: `FB_ARITHMETIC_INT`, `FB_ARITHMETIC_FLOAT`, `FB_COMPARE_FLOAT`.** Constructors default arithmetic to `+`; modes 1–4 are +, −, ×, ÷. IN1/IN2/Q are Integer (type 2) for INT arithmetic, Float (type 3) for FLOAT arithmetic; FLOAT comparator Q is Boolean (type 1). INT result is Java `char`, wrapping to unsigned 16-bit after each operation. Missing inputs return early and retain the prior output; caught cast/divide exceptions reset INT result to zero. Float arithmetic uses Java float32 and preserves IEEE division results (including infinity/NaN).

   FLOAT comparator source branch logic yields: mode 1 `a>b`, 2 `a<b`, 3 `a<=b`, 4 `a>=b`, 5 `a==b`, 6 `a!=b`. Its unusual inverted tests make NaN compare true for modes 1–4 and 6, false for 5. Missing inputs return early and retain prior Q. Preserve these source facts in explicit finite, NaN, missing and type-mismatch tests rather than silently applying a generic comparator's false default. Source SHA256: INT `2914b05cbda9f9b0a845b9d65682bc93f77c20fd4965eeb459f76b471953ae8f`; FLOAT `3385ba4c8a1df430d3ffe4ac64e3cc284ab10a7c7130c49171d18a2e95946192`; comparator `6658837671a8c6471da23d8b996ea0620948b0702ea44b0729ee14d3083b75ad`. Use distinct versioned block IDs and preserve existing generic BLOODSKY arithmetic, project JSON and unknown fields.

3. **Trigger F/R.** Original `FB_TRIGGER` has BOOL IN/Q, mode T/F/R (toggle/rising pulse/falling pulse), transient edge state. T is implemented; confirm F/R scan truth tables, reset/reconnect behavior and direct Android UI before enabling its source preview.

4. **Timer contract.** Constructor stores mode, time-unit code, elapsed timestamp and two latches. Labels do not establish behavior: source TP path appears not to set Q true. Verify constructor defaults, unit multipliers, each state transition, inversion and reset from complete method/source before representing it as Craft-compatible. Retain BLOODSKY TON/TOF/TP behavior as distinct IDs.

5. **Transport and macro blocks stay disabled.** `FB_MX` reads through `MyApplication.b().v0.I(address)`; `FB_ARRAY` writes via `v0.T(address,value)` on a rising enable. They cause original application Modbus side effects, so require register-space, transport, error, bounds and edge analysis. `FB_MACRO` uses a separate namespaced variable store keyed by macro unique ID and supports 1–4 named inputs plus typed output; parity needs lifecycle, nested graph ownership and persistence. `FB_POW` and `FB_MOVE` have empty `f()`, but compute in `getOut()`; they need pull-evaluation dependency and side-effect tests, not conclusions based on `f()` alone.

6. **Visual parity remains independent.** Most blocks inherit shared base rendering; labels M/O/Q, mode, scale and inversion alter appearance. Current gray bodies are partial source styling. Same-density screenshots, property dialogs, selection/disabled states and direct original-vs-BLOODSKY comparison remain required before any pixel-parity claim.
