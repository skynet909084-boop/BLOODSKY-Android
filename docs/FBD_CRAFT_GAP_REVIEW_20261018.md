## What remains

1. **Finish the two active candidates before widening scope.** CH_I/CH_F are implemented as distinct extended-palette blocks in PR #135; actual source-preview click and app restart coverage is stacked in #137. The full document-picker fix is #136. Their current emulator runs are pending, so none is accepted into #76 yet. Keep original icons gated.
2. **Next arithmetic batch: `FB_ARITHMETIC_INT`, `FB_ARITHMETIC_FLOAT`, `FB_COMPARE_FLOAT`.** The class source reveals exact modes 1–4 = +, −, ×, ÷; constructor default is +; IN1/IN2 and Q are typed Integer (type 2) for INT arithmetic and Float (type 3) for FLOAT arithmetic, while FLOAT compare Q is Boolean (type 1). INT arithmetic writes Java `char`, so result wraps to unsigned 16-bit after each operation. Integer divide-by-zero/cast exceptions reset result to zero. Float arithmetic uses Java float32; Java division retains IEEE Infinity/NaN behavior. Float comparator modes are 1 >, 2 <, 3 <=, 4 >=, 5 ==, 6 !=. Its decompiled inverted branch structure makes NaN behavior non-obvious; lock truth-table tests to the exact code before coding. Source hashes/method fragments are in artifact 12121443574; class SHA256: INT `2914b05cbda9f9b0a845b9d65682bc93f77c20fd4965eeb459f76b471953ae8f`, FLOAT `3385ba4c8a1df430d3ffe4ac64e3cc284ab10a7c7130c49171d18a2e95946192`, compare `6658837671a8c6471da23d8b996ea0620948b0702ea44b0729ee14d3083b75ad`. Add separate versioned IDs; preserve generic BLOODSKY arithmetic, existing project JSON and unknown fields.
3. **Trigger parity.** Original `FB_TRIGGER` has one BOOL IN and BOOL Q, modes T/F/R (toggle, rising pulse, falling pulse), and transient edge state. T is implemented, but F/R need exact scan truth tables, reset/reconnect behavior, and direct UI coverage before enabling the original preview. Inspect the entire source method, not only its labels.
4. **Timer contract.** The constructor stores timer mode, time-unit code, elapsed timestamp and two latches. Mode labels alone do not prove behavior: source TP has a suspicious path that may never assert Q. Verify constructor defaults, unit multipliers, each mode's state transitions, inversion and reset before representing it as original. Preserve BLOODSKY TON/TOF/TP conventions as separate IDs.
5. **Transport and macro features stay disabled.** `FB_MX` reads through original `MyApplication.b().v0.I(address)`; `FB_ARRAY` writes through `v0.T(address,value)` on a rising enable. These are application Modbus side effects, not pure math blocks. Need inspect register space, transport, error results, bounds and edge behavior before implementing. `FB_MACRO` uses a separate namespaced variable store keyed by macro unique ID and supports one to four named inputs plus typed output; reproducing it needs macro lifecycle, nested graph ownership and persistence, not a placeholder arithmetic block. The original `FB_POW` and `FB_MOVE` have empty `f()` methods but calculate via `getOut()`; only pull-evaluation with dependency and side-effect tests can establish their behavior.
6. **Visual parity is still separate work.** Most original blocks derive rendering from shared base classes; render details depend on labels M/O/Q, mode, scale and inversion. Existing gray body is a partial source style. Need same-density screenshots, property dialogs, selected/disabled states and a direct original-vs-BLOODSKY comparison before claiming pixel parity.
